## Context

提交工具栏当前已有拉取和推送入口；仓库状态由 `repoStore` 管理，提交历史由 `commitStore` 管理，当前选中 diff 与 Git 操作状态由 `selectionStore` 管理。自动 Fetch 已被移除，因此需要提供用户可控的本地刷新和单独 Fetch 操作。Fetch 由 Tauri 后端执行，前端调用通过 `invoke` 完成。

## Goals / Non-Goals

**Goals:**
- 复用现有 store 读取仓库数据的路径，刷新仓库状态、提交历史、操作/冲突状态和当前 diff。
- 将本地刷新与远程 Fetch 分成两个入口；本地刷新不调用网络命令。
- 为手动 Fetch 设置 30 秒超时，在超时时终止 Git 子进程并向前端返回错误。
- Fetch 无论成功还是失败，都刷新本地展示，并释放操作进度。

**Non-Goals:**
- 恢复打开仓库、切换仓库或应用聚焦时的自动 Fetch。
- 改变 Pull、推送或分支快进更新的既有行为。
- 新增事件、持久化字段或通用 Git 命令超时策略。

## Decisions

- 在提交工具栏把“刷新”和“获取远程”作为独立按钮，统一通过 `selectionStore.currentOp` 显示忙碌状态并阻止重复触发。
- 在选择状态 store 编排刷新：调用仓库状态刷新、提交列表刷新、操作状态检查，再重新读取当前选中提交 diff；工作区 diff 通过一个轻量刷新触发值重新加载。
- 后端新增专用 `git_fetch(path)` 命令，使用现有 Git 执行环境运行 `git fetch`。使用 Tokio 超时和 `kill_on_drop` 仅约束此 Fetch 命令，错误通过 Tauri 命令的 `Result<(), String>` 传回。
- 将当前选中提交 diff 的重新读取结果作为有效性检查；如果 Git 无法读取该提交，则回到工作区选择，避免保留失效提交 diff。
- Fetch 的刷新放在 `finally` 路径执行：即使 Git 报错或超时，也重新读取仓库状态和远程跟踪引用，然后向用户展示原始 Fetch 错误。

## Risks / Trade-offs

- `[外部 Git 进程超时]` → `kill_on_drop` 确保被包装的 Git 进程在超时时被终止；随后无论命令结果如何都会刷新本地状态。
- `[刷新期间仓库被其他工具再次修改]` → 本操作展示刷新完成时 Git 返回的状态；用户可再次点击刷新获取后续变更。
- `[无远程配置或网络不可用]` → 后端原样返回 Git 错误，前端结束进度并提示失败，同时仍刷新本地视图。

## Migration Plan

无需数据迁移。新增前端入口和 Tauri 命令后即可使用；如果需要回滚，移除入口、命令及其专用超时执行方法即可。既有本地状态和远程配置不变。

## Open Questions

无。入口、Fetch 行为和 30 秒超时已由需求确认。
